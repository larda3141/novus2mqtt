# novus2mqtt

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](https://opensource.org/licenses/MIT)
[![Rust](https://img.shields.io/badge/rust-2021-orange.svg)](https://www.rust-lang.org/)

A Rust-based MQTT bridge for Paul Novus 300 ventilation systems, enabling seamless integration with **Home Assistant**. Parses the RS485 serial bus, publishes sensor data to MQTT, and supports bidirectional control via Home Assistant discovery.

## Features

- **RS485 Bus Parsing**: Direct serial communication with Paul Novus devices (9600 baud default)
- **Multi-Register Splitting**: Handles multi-byte register values from the bus
- **MQTT Publishing**: Publishes sensor data and accepts control commands
- **Home Assistant Discovery**: Automatic entity creation (sensor, number, select) with proper device classes
- **Bridge Diagnostics**: Runtime metrics and connection status published to MQTT
- **Bus Dump Recording**: Record raw bus traffic to file for offline analysis
- **NTP Time Sync**: Optionally synchronize device time via NTP
- **Interactive Keyboard Commands**: Runtime control from the terminal
- **CalVer Versioning**: `YYYY.M.D` format, auto-generated by `build.rs`
- **Configuration Validation**: `cargo run -- validate-config` checks config before running
- **Health Check**: `cargo run -- health-check` verifies connectivity

## Prerequisites

- Rust toolchain (stable, 2021 edition)
- Access to serial port (e.g., `/dev/ttyUSB0`)
- MQTT broker (e.g., Mosquitto)

## Quick Start

1. Clone the repository:
   ```bash
   git clone https://github.com/larda3141/novus2mqtt.git
   cd novus2mqtt
   ```

2. Create a `.env` file (auto-loaded via `dotenvy`):
   ```bash
   cat > .env << EOF
   MQTT_BROKER=your-mqtt-broker-ip
   MQTT_USERNAME=your-username
   MQTT_PASSWORD=your-password
   MQTT_BASE_PREFIX=novus2mqtt
   HASS_DISCOVERY=true
   HASS_DISCOVERY_PREFIX=homeassistant
   EOF
   ```

3. Build and run:
   ```bash
   # Development
   cargo run

   # Production (optimized release build)
   ./build.sh
   ./target/release/novus2mqtt
   ```

## CLI Usage

# Run the bridge

## Configuration

### Environment Variables

All environment variables can be set in a `.env` file (loaded automatically) or exported in the shell.

| Variable | Description | Default |
|----------|-------------|---------|
| `MQTT_BROKER` | MQTT broker hostname/IP | Required |
| `MQTT_PORT` | MQTT broker port | `1883` |
| `MQTT_USERNAME` / `MQTT_PASSWORD` | MQTT credentials | None |
| `MQTT_BASE_PREFIX` | Base topic prefix | `novus2mqtt` |
| `MQTT_CLEAR_ON_START` | Clear retained topics on startup | `false` |
| `MQTT_TLS` / `MQTT_TLS_INSECURE` | TLS settings for MQTT | `false` |
| `SERIAL_PORT` | Serial device path | `/dev/ttyUSB0` |
| `SERIAL_BAUDRATE` | Serial baud rate | `9600` |
| `LOG_LEVEL` | Log level (trace, debug, info, warn, error) | `info` |
| `LOG_FORMAT` | `human` or `json` | `human` |
| `LOG_FILE` / `ENABLE_FILE_LOGGING` | Optional rotating log file | None |
| `NOVUS_CONFIG` | Path to unit identity YAML | `config/device.yaml` |
| `NOVUS_REGISTERS` | Path to register-map YAML (defaults to sibling of `NOVUS_CONFIG`) | `config/registers.yaml` |
| `HASS_DISCOVERY` | Enable Home Assistant discovery | `false` |
| `HASS_DISCOVERY_PREFIX` | HA discovery topic prefix | `homeassistant` |
| `HASS_DEVICE_DISCOVERY` | Publish device-level discovery | `false` |
| `HASS_DISCOVERY_MODE` | `startup` or `lazy` | `startup` |
| `AUTO_SYNC_TIME` | Write system time to VMC every hour (⚠ see note below) | `false` |
| `REQ_MEM_ON_STARTUP` | Request one 0x83 memory-dump at startup so HA fills faster. Off = passive (TFT not disturbed, values arrive within ~30 s anyway) | `false` |
| `HIGHLIGHT_UNKNOWN_REGS` | Magenta/cyan alerts for unknown and TBC registers (see [reverse engineering](#reverse-engineering)) | `true` |
| `ACTIVITY_LOG` | Per-register live logging (`RECV`/`SEND` lines, see [Output formats](#output-formats)) | `false` |
| `THROTTLE_MAX_INTERVAL` | Global heartbeat in seconds (see [MQTT publish throttling](#mqtt-publish-throttling)) | `0` |
| `THROTTLE_MIN_CHANGE_PCT` | Global relative-change threshold in % | `0` |
| `SUMMARY_INTERVAL` | Message-summary log cadence in seconds (0 = off) | `10` |
| `BUS_DUMP_FILE` | File path to record raw bus traffic | None |
| `MAX_MEMORY_MB` | Memory guard threshold (0 = off) | `0` |

> **`AUTO_SYNC_TIME` caveat:** enabling this makes the connector write date/time
> registers every hour at HH:49. The VMC responds with `0x88` frames (observed
> for ~20 s during the first few hourly syncs after startup — see
> [BACKGROUND.md](BACKGROUND.md) "Observed: 0x88 fires only on our hourly time-sync").
> Leave it `false` unless you specifically need RTC sync and can tolerate the
> bus disturbance at HH:49.

### Device Configuration

Configuration is split across two YAML files in `config/`:

- **`device.yaml`** — unit identity (name, hw/sw version, serial number, variant
  left/right). Edit this to match your specific unit. ~20 lines.
- **`registers.yaml`** — the full register map: sensor entries (RO), control
  entries (RW), payload types, MQTT topics, Home Assistant discovery metadata.
  This is static and shared across installs; you normally do not edit it.

Both files are loaded together by `config.rs::DeviceConfig::load` — point
`NOVUS_CONFIG` at `device.yaml` and `registers.yaml` is auto-discovered in the
same directory (override with `NOVUS_REGISTERS` if needed).

The bus protocol itself (frame format, command codes, known quirks) is
documented in [BACKGROUND.md](BACKGROUND.md).

### MQTT publish throttling

The VMC rebroadcasts most registers every ~5 seconds — without throttling, MQTT
and Home Assistant get a flood of identical messages. The app has a per-register
**deadband + heartbeat + rate-limit** throttle that suppresses unchanged values
and spaces out updates, while still guaranteeing periodic refreshes.

Throttling is configured at two levels:

1. **Global defaults** in `.env` — apply to every register unless overridden.
2. **Per-register `throttle:` block** in `registers.yaml` — overrides the globals
   for that one register.

#### Yaml per-register block

```yaml
- address: '0x81'                # Temperature Sensor T2
  ...
  throttle:
    min_change: 0.2              # absolute numeric delta in the decoded unit
    min_change_pct: 1.0          # relative delta as % of the previous value
    max_interval: 300            # heartbeat seconds — publish anyway if older
    min_interval: 60             # rate-limit ceiling — never publish sooner
```

All four fields are optional. Any combination is valid; the app falls back to
global defaults for fields you omit (except `min_interval`, which is per-register
only — rate-limiting doesn't make sense applied to everything).

Additional per-register switches that interact with throttling:

```yaml
  mqtt_publish: false            # completely disable MQTT publish for this reg
  suppress_activity: true        # don't even show in the activity log
```

#### Global defaults in `.env`

```
THROTTLE_MAX_INTERVAL=0          # heartbeat seconds (0 = no heartbeat)
THROTTLE_MIN_CHANGE_PCT=0        # relative change % threshold (0 = no percent rule)
```

When **both globals are 0** AND a register has **no `throttle:` block**, that
register falls back to legacy behaviour: publish every RECV, no throttling.

#### Decision flow (in order)

For every decoded register value:

1. `mqtt_publish: false` → **`[omitted]`** — no publish.
2. First value since startup → **`[published: new]`** — no prior state to throttle against.
3. No throttle configured anywhere → **`[published: changed]`** (hex differs) or **`[published: stale]`** (hex same) — legacy always-publish behaviour.
4. `age < min_interval` → **`[skipped: rate]`** — ceiling beats everything except "first value".
5. `age ≥ max_interval` → **`[published: stale]`** — heartbeat refresh.
6. Hex bytes identical to previous → **`[skipped: held]`** — no change at all.
7. Numeric **and** `|Δ| ≥ min_change` or `|Δ%| ≥ min_change_pct` → **`[published: changed]`**.
8. Numeric **and** change below both thresholds → **`[skipped: delta]`**.
9. Non-numeric changed (hex differs) → **`[published: changed]`**.

### Outcome-tag cheatsheet

| Tag | Meaning |
|---|---|
| `[published: new]` | first decoded value of the register since startup |
| `[published: changed]` | value differs from the last one we published (threshold met or no threshold) |
| `[published: stale]` | value unchanged but heartbeat fired (or no throttle, so we always publish) |
| `[skipped: held]` | bytes identical to last publish, no heartbeat due yet |
| `[skipped: delta]` | numeric value moved but less than the configured threshold |
| `[skipped: rate]` | published too recently — `min_interval` ceiling not yet elapsed |
| `[omitted]` | `mqtt_publish: false` on this register — never published |

The outcome tag appears at the end of every activity-log line (see
[Console / log output](#console--log-output) below), so you can see at a glance
whether a value made it to MQTT and why.

#### Example: tune a temperature sensor for HA

Suppose you want temperatures to update when they move by at least 0.2 °C, and
to always refresh at least once every 5 minutes even if held steady:

```yaml
- address: '0x82'                # Intake Air Temperature
  throttle:
    min_change: 0.2
    max_interval: 300
```

Activity-log output at different moments:

```
0x82 Intake Air Temperature <- 21.0 °C    [published: new]
0x82 Intake Air Temperature <- 21.0 °C    [skipped: held]
0x82 Intake Air Temperature <- 21.1 °C    [skipped: delta]    ← Δ=0.1 < 0.2
0x82 Intake Air Temperature <- 21.2 °C    [skipped: delta]
0x82 Intake Air Temperature <- 21.3 °C    [published: changed] ← Δ=0.3 ≥ 0.2
...5 min later with no changes...
0x82 Intake Air Temperature <- 21.3 °C    [published: stale]  ← heartbeat
```

#### Example: a register that changes every RECV (Time)

`0x02 Time` ticks the seconds value every broadcast, so every hex is different
and `[skipped: held]` never applies. Use `min_interval` to rate-limit:

```yaml
- address: '0x02'                # Time
  throttle:
    min_interval: 60             # at most once per minute
    max_interval: 300
```

Now Time publishes on startup, then at most once every 60 seconds.

#### Throttling state is in-memory

The "last published" value and timestamp are kept per register inside the
running process. Restarting the app resets state — the first decoded value of
each register after a restart always publishes (rule 2 above).

## MQTT Topics

Each register publishes to a topic under the base prefix:

```
{MQTT_BASE_PREFIX}/{device_id}/{semantic_topic}/state
```

The `device_id` is auto-generated from the device config: `{model}-{serial_number}` in lowercase (e.g., `novus300-000741929834`). If no serial number is configured, a hash of the device metadata is used instead.

### Examples

| Register | Topic |
|----------|-------|
| Bus Version | `novus2mqtt/{device_id}/system/bus_version/state` |
| Vent Level | `novus2mqtt/{device_id}/ventilation/level/state` |
| Temperature T2 | `novus2mqtt/{device_id}/temperatures/t2/state` |

### Payload Format

State payloads are JSON with raw hex and decoded value:
```json
{
  "hex": "dc 00",
  "converted": 22.0,
  "formatted": "22.0 °C"
}
```

Enum entities also include available options:
```json
{
  "hex": "01",
  "converted": "English",
  "options": ["German", "English", "French", "Dutch"]
}
```

### Status Topics

- `{base}/status` - Bridge connection status and version
- `{base}/diagnostics` - Runtime diagnostics (message counts, uptime, errors)

## Home Assistant Integration

Requires the [MQTT integration](https://www.home-assistant.io/integrations/mqtt/) configured in Home Assistant with a working MQTT broker (e.g., Mosquitto).

When `HASS_DISCOVERY=true`, entities are automatically created via [MQTT Discovery](https://www.home-assistant.io/integrations/mqtt/#mqtt-discovery):

- **Sensors**: Temperatures, operating hours, filter status, error codes
- **Numbers**: Fan speed percentages, temperature thresholds
- **Selects**: Ventilation levels, operating modes, frost protection

All entities appear grouped under a single device in HA. Entity categories are set so that controls, configuration parameters, and diagnostic sensors are properly separated in the HA UI.

## Deployment

### Running as a systemd Service

For production use, run novus2mqtt as a system service that starts on boot and restarts automatically:

1. Build the release binary:
   ```bash
   cargo build --release
   ```

2. Install binary and config:
   ```bash
   sudo cp target/release/novus2mqtt /usr/local/bin/
   sudo mkdir -p /etc/novus2mqtt
   sudo cp config/device.yaml /etc/novus2mqtt/
   sudo cp .env /etc/novus2mqtt/
   ```

3. Create the service file:
   ```bash
   sudo tee /etc/systemd/system/novus2mqtt.service << 'EOF'
   [Unit]
   Description=novus2mqtt - Paul Novus MQTT Bridge
   After=network-online.target mosquitto.service
   Wants=network-online.target

   [Service]
   Type=simple
   User=pi
   Group=dialout
   EnvironmentFile=/etc/novus2mqtt/.env
   ExecStart=/usr/local/bin/novus2mqtt --novus-config /etc/novus2mqtt/device.yaml
   Restart=on-failure
   RestartSec=10

   # Hardening
   ProtectSystem=strict
   ProtectHome=true
   ReadWritePaths=/tmp
   NoNewPrivileges=true

   [Install]
   WantedBy=multi-user.target
   EOF
   ```

4. Enable and start:
   ```bash
   sudo systemctl daemon-reload
   sudo systemctl enable novus2mqtt
   sudo systemctl start novus2mqtt
   ```

5. Useful commands:
   ```bash
   sudo systemctl status novus2mqtt     # Check status
   journalctl -u novus2mqtt -f          # Live logs (like "reattach")
   journalctl -u novus2mqtt --since today  # Today's logs
   sudo systemctl restart novus2mqtt    # Restart
   sudo systemctl stop novus2mqtt       # Stop
   ```

### Running with tmux (Development)

For interactive sessions where you want keyboard commands:

```bash
# Start in a detachable session
tmux new -s novus2mqtt './target/release/novus2mqtt'

# Reattach anytime
tmux attach -t novus2mqtt

# Detach without stopping: Ctrl+B, then D
```

#### Interactive Keyboard Commands

While running in a terminal (or tmux), the following single-key commands are available:

| Key | Command | Description |
|-----|---------|-------------|
| `d` | dump | Request full memory dump from bus master (queues a 0x83 frame) |
| `t` | time | Force time sync (writes system clock to Novus) |
| `s` | stats | Show live statistics (bus/MQTT counters, CPU, memory) |
| `m` | **marker** | Insert a planned marker (`M1, M2, …`) into the bus dump file + stdout. Use to annotate reverse-engineering sessions — press before each action. Counter resets on app start. |
| `f` | **bookmark** | Insert an unplanned bookmark (`B1, B2, …`). Same idea as a marker but reserved for unexpected events. |
| `p` | **pause** | Stop live display of the activity stream. New RECV/SEND lines are **buffered** (capped at 10 000 lines) until you press `r` — on resume they're replayed in order with their original wall-clock timestamps. |
| `b` | **blackout** | Stop live display of the activity stream. New RECV/SEND lines are **dropped**; only a count is kept. Press `r` to resume live (you'll see how many were dropped). |
| `r` | **resume** | Return to live mode. If paused, replays the backlog first. If blacked out, prints how many lines were dropped. |
| `h` | **highlight** | Prompts for a register address (e.g. `0x55`), then shows matching activity lines in bold bright white so they stand out. Press `h` again to add more addresses. |
| `H` | clear highlights | Removes all active highlight addresses. |
| `?` | help | Show keyboard command list + active highlights |
| `q` / `x` | quit | Graceful shutdown |

The marker/bookmark workflow is designed for reverse-engineering sessions — see
[`scripts/rev_eng/`](scripts/rev_eng/) for the step-by-step action scripts this
feature supports.

## Output formats

### Console / log output

Every log line carries two elapsed-time fields after the wall-clock timestamp:

```
2026-04-16T08:48:26.350Z [t+00:00:01 Δ--:--:--]  INFO novus2mqtt::app: starting main loop
2026-04-16T08:48:35.142Z [t+00:00:10 Δ00:00:09]  INFO novus2mqtt::app: message summary ...
⚑ MARKER M1  [t+00:00:15]  [Δ--:--:--]  → written to bus dump         ← bold yellow
2026-04-16T08:48:48.003Z [t+00:00:23 Δ00:00:08]  INFO ...              ← Δ now counts from M1
⚑ BOOKMARK B1 [t+00:01:04]  [Δ00:00:41]  → written to bus dump        ← bold red
2026-04-16T08:49:12.001Z [t+00:01:12 Δ00:00:08]  INFO ...
```

- `t+HH:MM:SS` — uptime since app start.
- `ΔHH:MM:SS` — time since the last marker/bookmark. Displays `--:--:--`
  before any marker is pressed. Resets on every `m` or `b` press.
- Marker lines are **bold yellow**, bookmark lines are **bold red** (only when
  stderr is a TTY — pipes and redirections stay plain text).

#### Per-register activity lines (`ACTIVITY_LOG=true`)

When `ACTIVITY_LOG=true`, every decoded register is printed as a single line:

```
INFO reg: 0x7b Frost Protection Mode <- Safe         [published: new]
INFO reg: 0x81 Temperature Sensor T2 <- 22.0 °C      [skipped: delta]
INFO reg: 0x44 System Status Bitmask <- 0x5c         [omitted]
INFO reg: 0x02 Time <- 15:14:23                      [skipped: rate]
INFO reg: 0x7b Frost Protection Mode -> Eco          [published: changed]  ← SEND from us
```

- `<-` = RECV (VMC broadcast observed on the bus).
- `->` = SEND (a write we initiated, typically from an MQTT command).
- The trailing tag comes from the [throttle decision flow](#decision-flow-in-order);
  it tells you whether the decoded value actually reached MQTT or was suppressed.

Registers marked `suppress_activity: true` in `registers.yaml` (e.g.
`0x44 status_bitmask`, `0x55 fan_speed`) stay silent regardless of
`ACTIVITY_LOG` to avoid drowning the console in high-rate background chatter.

### Bus dump file (`BUS_DUMP_FILE`)

When the env var is set, every raw bus frame is recorded plus any markers:

```
1776329041.507 < 01 09 84 00 79 3f                ← received frame
1776329041.508 > 01 01 83 00 4f 0f                ← frame sent by us
1776329056.782 # MARKER M1 t+00:00:15 Δ--:--:--   ← marker press
1776329097.231 # BOOKMARK B1 t+00:00:56 Δ00:00:41 ← bookmark press
```

Format: `{unix_timestamp_sec:.3} {direction} {hex_bytes…}` where direction is
`<` (received), `>` (sent), or `#` (marker/bookmark annotation).

Rotation: if the configured file already exists, the next run uses
`{stem}.N.{ext}` (e.g. `bus_dump.log` → `bus_dump.1.log` → `bus_dump.2.log`).

Useful awk filters:

```bash
awk '$2=="<"' bus_dump.log       # only received frames
awk '$2==">"' bus_dump.log       # only frames we sent
awk '$2=="#"' bus_dump.log       # only markers/bookmarks
```

### Running via MQTT (Headless)

Even without terminal access, you can control the bridge via MQTT:

```bash
# Request memory dump
mosquitto_pub -h <broker> -t 'novus2mqtt/<device_id>/bus/system/dump/set' -m '1'

# Force time sync (publish current time to command topics)
mosquitto_pub -h <broker> -t 'novus2mqtt/<device_id>/bus/system/time/set' -m '23:45:00'
mosquitto_pub -h <broker> -t 'novus2mqtt/<device_id>/bus/system/date/set' -m '2026-04-15'

# Monitor diagnostics
mosquitto_sub -h <broker> -t 'novus2mqtt/<device_id>/diagnostics'
```

## Reverse engineering

See [`scripts/rev_eng/`](scripts/rev_eng/) for guided markdown scripts that walk
the TFT panel menus and instruct you when to press `m` (marker) or `b`
(bookmark). The resulting bus-dump windows between markers are what gets
analysed to map display actions onto register writes. Script `01` is a
read-only walk; `02`–`04` cover low-risk write tests.
